# grounding-eval —— 判断「抽出来的待办有没有材料依据」

一条纠错闸门：把模型从材料里抽出的待办逐条拿回材料里核对，输出「有依据 / 疑似无依据」，
**只打标，绝不自动删除**。附带一个跨语言方案（中译英 → 英文 MiniCheck）和它的实测代价。

```
材料（records/）──┐
                  ├─ 联合翻译（一份材料 + 它的全部断言，一次调用）──→ 英文
待办（todos/items）┘                                             │
                                                                 ▼
                                              MiniCheck（Flan-T5）打分 → supported?
                                                                 │
                                                      只打标，交给人复核
```

## 为什么需要这层

抽取模型的错误有两类：**漏**（材料里有、没抽出来）和**编**（材料里没有、硬写一条）。
调提示词能压住一部分，但压不干净；而待办这种东西，一条编造的「明天交表」比漏掉三条更糟。
所以要有一个**独立的**判断层：它不生成，只核对。

## 快速开始

```bash
pip install -r requirements.txt

# 1) MiniCheck 权重（Flan-T5-Large 版）
huggingface-cli download lytang/MiniCheck-Flan-T5-Large \
  --local-dir ckpt/flan-t5-large

# 2) 把一个本地 LLM 起在 8080（用于翻译），或设置 LLM_API
# 3) 跑样例（相对 record_path，从仓库根目录执行）
python3 verify.py --items samples/items --out /tmp/verify.jsonl
```

输出（示意）：

```
材料 notice-2026-11-05  （2 条待办）
   ✓              参加社团交流活动（上午场/下午场）
        p=0.96
   ⚠️ 疑似无依据   11月9日提交报名表到社团办公室
        p=0.12

  未标记（MiniCheck 判有依据）   1/2
  ⚠️ 疑似无依据                1/2
```

第二条是**故意写的反例**：材料说的是 11 月 6 日 18:00 前，待办却写成 11 月 9 日。
它会被标出来，但不会被删掉。

## 输入格式

`--items` 指向一个目录，里面每个 `*.md` 带 front-matter：

```markdown
---
task: 参加社团交流活动
start_date: 2026-11-08
end_date: 2026-11-08
record_path: samples/records/notice-2026-11-05.md
---
```

`record_path` 可以是：

- 一个文件（文本材料）→ 直接读全文
- 一个目录（图片 OCR 打包）→ 读 `text.md`，并去掉 `## OCR 文本` 之前的中文头

路径可以是绝对的，也可以是相对当前工作目录的。

## 设计要点（都是实测出来的）

### 只用一个验证器：MiniCheck

这里一度是「中文 NLI + MiniCheck 双验证器，一致才放行」。在 33 条带标签的测试集上：

| 方法 | 判对 | 漏报（编造判成有依据） | 误报 |
|---|---|---|---|
| **翻译 + 英文 MiniCheck** | **32/33 (97%)** | **0** | 1 |
| 本地 4B 模型当裁判（逐条问） | 32/33 (97%) | 0 | 1 |
| 中文 NLI（Erlangshen-330M） | 28/33 (85%) | 1 | 4 |

NLI 的 2 条误报是系统性的：材料写「拒绝公式排版内耗！一小时掌握公式编辑技巧」（一场讲座），
NLI 坚持认为它推不出「参加」这个动作，判为矛盾 —— 它把「材料没明说你会去」当成「不支持」，
而流水线要抽的恰恰是「该做什么」。真跑在 12 条真实待办上，NLI 标记 2 条、真命中 0 条；
MiniCheck 标记 1 条、真命中 1 条、**零误报**。

**漏报 0 是纠错闸门的底线**，所以取 MiniCheck。

### 译文必须「一份材料 + 它的全部断言」联合翻译

分开译会让同一活动出现 5 种英文名，MiniCheck 从 32/33 掉到 28/33。
`verify.py` 的 `translate()` 把文档和每条断言放在一次调用里，并要求输出固定标记
（`===DOC=== / ===CLAIM n===`），缺段直接报错。

### 不要告诉模型「这条可能没依据」

实测：把「有核查程序认为这条没依据」作为提示喂回去，会触发顺从，正确条目被删掉 3/4；
换成不给任何先验的中立措辞，正确条目 4/4 全保住（4 种措辞结果一致）。
所以本项目**只打标**，不把判定结果反馈给抽取模型。

### 中文直喂为什么不行

MiniCheck 的 Flan-T5 分词器会把中文断言整条吃成 `<unk>`；实测中文 28/33，
换成英文译文 **18/33**（误报 4 → 14）—— 因为 NLI 那套中文词表切英文会碎成 `st/##ude/##nt`。
所以在中文场景，**翻译这一层是必需的**，而它本身也是新的误差源（日期、数字最容易走样），
译文要留存供人工核对。

### 失败必须显式

模型加载不了、LLM 不通、翻译输出缺段 —— 一律报错退出，**绝不静默降级**。
（本机曾出现 llama.cpp 在受限环境里静默退回 CPU、速度掉 5 倍而状态仍显示 GPU 的情况，
这类「看起来成功」的失败比直接报错危险得多。）

## 要求

- Python 3.10+
- `torch`、`transformers`（MiniCheck）
- 一个 OpenAI 兼容的本地 LLM（默认 `http://127.0.0.1:8080/v1/chat/completions`，
  可用 `LLM_API` 覆盖）
- MiniCheck 权重放在 `ckpt/flan-t5-large`（可用 `MINICHECK_DIR` 覆盖）

## 文件

```
verify.py           主工具：读 items → 联合翻译 → MiniCheck 打分 → 打标
mc_score.py         MiniCheck 的推理复现（CPU，单块断言）
nli_score.py        中文 NLI 基线（对照用）
translate.py        批量翻译工具（材料/断言）
translate_fixed.py  修翻译缺段后重跑
samples/            合成样例（1 份材料 + 2 条待办，其中 1 条是反例）
ckpt/               MiniCheck 权重（不随仓库分发）
```

## 已知边界

- 只判断「材料是否支持这条待办」，不判断「这条待办是否该做」
- 长材料会被切成多块（MiniCheck 的 500 词分块）；本项目断言单块，出现多块会直接报错
- 翻译质量决定上限：日期、数字、专有名词在译文里走样会直接变成误报
- 样例里的 `record_path` 是相对路径，换目录运行会找不到材料
